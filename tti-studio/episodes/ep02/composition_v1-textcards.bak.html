the one analogy for tonight

Picture a restaurant.

The dining room = CLIENT
Where you sit & order.
Pleasant, interactive — but no food is cooked here.
The kitchen = SERVER
Where the food is made.
Hidden, follows the recipes, guards the pantry.
The waiter carrying orders back and forth? That's coming up.
the client · the frontend

Your phone is the dining room.

Client · runs on your device
  • Shows the screen
  • Handles your taps & typing
  • Plays the animations
  • Asks the server for things
It's the part you see and touch — the browser, or the Swiggy app in your hand.
the server · the backend

The kitchen runs the show.

Server · runs far away
  • Runs the business logic
  • Enforces the rules
  • Owns the data (the database)
where does the data live?

The database is always server-side.

Client holds
A temporary copy.
Just what's on screen right now. Close the app and it's gone.
Server owns
The real, permanent data.
Refresh the page and the truth comes from the server.
Your phone is a window onto the data — not where it's kept.
the golden rule of system design

Never trust the client.

Anyone can edit their own device. The server has the final say — every time.
the api · the waiter

One kitchen. Many dining rooms.

Why split it? Security (rules in one place), reuse (many apps, one backend), scale each side alone.
who draws the screen?

Server-side vs client-side rendering.

SSR · server-side
Page arrives ready.
Server builds the full page. Fast first view, great for search. But more work per request.
CSR · client-side
Browser builds it.
Server sends a near-empty page + code. Smooth, app-like after load. But slower first paint.
Most big apps do both — SSR for the first screen, CSR after. It's a trade-off, not a winner.

Meet the IP address.

It's the server's phone number. (Older ones look like this — IPv4; newer IPv6 ones are far longer.)
names in, numbers out

DNS is the internet's phonebook.

DNS lookup
swiggy.com→142.250.193.4
You tap a saved contact's name; your phone dials the number. Same idea.
You remember swiggy.com. DNS remembers the number.
// the dns lookup

Finding the number is a relay race.

Root and TLD don't know the address — they just say "ask them next."
look it up once, remember it

The second visit is instant.

Cached
Your device remembers the number.
No relay race next time — it's already saved.
TTL · the trade-off
Fast vs fresh.
Keep it long = fewer trips, but slow to update. Short = always fresh, more trips.
One myth to drop: DNS only finds the address. It never loads the page itself.

two everyday verbs

GET reads. POST writes.

GET · /restaurants
Browse the menu.
Just looks, changes nothing. Safe to repeat. Rides in the URL — bookmarkable.
POST · /order
Place the order.
Changes things on the server. Data rides in the body, not the URL.
⚠ Send a POST twice and you can place two orders. (We fix that in a later episode.)

Headers are little labels on every request. The login cookie is the one that says "it's me again."
how it went

Every answer comes with a code.

200OK — here's what you asked for
301Moved — it's over here now (follow the arrow)
404Not found — that page doesn't exist (your side)
500Server error — the kitchen broke (their side)
Easy rule: 4-something = your fault, 5-something = the server's fault.
the s is for secure

HTTP is a postcard. HTTPS is a sealed envelope.

the padlock = encrypted in transit
Your phone and the server quietly agree on a shared secret (the server proves who it is with a certificate), then scramble every message. No one in between can read it.
Careful: the padlock means encrypted, not "trustworthy." Scam sites can have one too.
